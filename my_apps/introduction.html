1.3 – 1.4 Sensors & Architecture

Sensors are the monitoring nervous system of the machine.

Temperature Sensor

Checks water heating tank; MCU only allows hot water into brewing once ~92°C is reached, matching optimal extraction standards.

Weight Sensor (Load Cell)

Under the cup platform — stops pumps automatically at the correct pour weight, reducing overflow and improving consistency.

Raw Material Tank Load Cell

Measures remaining stock of beans/powder; data feeds the inventory-forecasting AI on the CPU.

Water Pump Vibration Sensor

Monitors abnormal shaking; unusual patterns are reported to the predictive-maintenance AI for early warning.

1.5 AI Selection

The AI value is backstage: fewer stockouts and earlier repairs.

Inventory Forecasting

Load cells track remaining raw materials. The CPU uses AI-based demand forecasting to predict consumption rates and trigger restock notices before ingredients run out.

Predictive Maintenance

Vibration and current signals reveal abnormal pump behaviour — blockages and wear — before complete mechanical failure occurs.

Stock Example: if bubbles are predicted to run out within 2 hours, the system updates the UI and removes affected drinks from the menu, syncing the inventory database instantly.

Maintenance Example: if a pump is likely to fail within 48 hours, the system reduces its operating frequency and sends a replacement reminder automatically.

2.1 – 2.2 Transport Protocols

TCP protects payments; UDP keeps screen media smooth.

Protocol Description & Use Case
TCP — Connection-Oriented Three-way handshake, ACK packets, and retransmission guarantee accuracy and order. Best for credit card / e-wallet payment data, where Deduction → Settled must occur in strict chronological order.
UDP — Connectionless No handshake, smaller headers, zero ACK overhead — very fast, low latency. Best for live video advertisements: a lost frame causes a tiny imperfection, not a freeze.

The system is not single-protocol. It chooses TCP or UDP based on the risk and timing needs of each data type — a hybrid scheme by design.

3. Ingredient & Inventory Database

The database decides whether the machine should accept the order.

1. Pre-Purchase

Local database checks recipe, ingredients & supplies. If insufficient, displays "cannot be made" and signals the server it needs restocking.

2. Purchase

Payment with a time limit produces a Proof-of-Purchase (POP) ID on success; the transaction record is stored online — otherwise the order is nulled.

3. Post-Purchase

Recipe fetched from server, drink made, stock updated. If ingredients now run low, system requests restock and hides affected drinks.

(Data Flow Diagram): Customer → Places order → Local Database checks ingredients → syncs to Server; Payment → POP produced → Makes ordered beverages → updates ingredient stock.
